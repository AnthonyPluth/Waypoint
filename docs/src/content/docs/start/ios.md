The Waypoint iPhone app is a native shell around your own Waypoint. It signs in to the server you point it at; nothing goes through anyone else's server except an optional wake-up signal for notifications.

## Signing in

The app opens a system sign-in sheet to your server's `/oauth/authorize` page. The sheet is private: iOS shows no consent prompt of its own, but it doesn't share Safari's logins, so you sign in to your OpenID Connect provider each time you sign in to the app. Waypoint sends you through your OpenID Connect provider first, then shows **Waypoint for iPhone wants to connect to Waypoint** with **Allow** and **Deny**. Allowing sends you back to the app with a one-time code, which the app swaps for a token using PKCE.

This needs `WAYPOINT_PUBLIC_URL` set, the same as [connecting an assistant](/Waypoint/start/mcp/). A Waypoint with no sign-in of its own (`OIDC_ISSUER` unset) needs no sign-in at all; the app just opens it.

## What the app can reach

The token has the `app` scope and is for `<WAYPOINT_PUBLIC_URL>/app` only. The server accepts it as a `Bearer` token on the web app's `/api/` routes, as you, so the app can do everything the web app can. It is never accepted on `/mcp`, and an assistant's token is never accepted on `/api/`.

The app's web view is given a normal web session by `POST /auth/app-session`, which needs a valid app token and the `X-Waypoint: 1` header.

## Saved trips

The app can keep your trips on the phone. Saving is on by default and is per phone: it is on after a new install, and also on a phone where the app was already installed and is updated to a version with this switch, so that phone starts saving your trips without you choosing it. To stop it, switch off **Save my upcoming trips** in **Settings → Offline & notifications → Offline access**; switching it off deletes the saved trips at once, and there is no separate Remove. The first save happens when you open Waypoint online after signing in, and signing in again turns saving back on. The card lists what is saved and when, and says **Couldn’t save the trips** when a save failed. An older version of the app without this switch shows no Offline access card.

With saving on, the app reads `GET /api/offline` with its own token when you open Waypoint after signing in, each time you return to the app and when you switch saving on, and replaces the saved set with the reply. Only the trips you are on are in it, and it never holds loyalty or Known Traveler numbers (see [Offline access](/Waypoint/start/offline/)). The copy includes the QR code of the parking bookings you can see on those trips (the owner’s decision, 2026-11-18), shown in the QR code dialog when the app can’t reach your server; the saved trip's page has a **Show QR code** button for it. It is stored with the trips under the same file protection and is deleted and replaced with them. The reply carries a `version`; the app saves only a version it knows and otherwise keeps the copy it has. If the save fails (the phone can't reach the server, or the server answers with an error), the copy it has stays, the card says **Couldn’t save the trips**, and the app tries again the next time you open Waypoint online.

The saved trips are files in the app's private storage inside its sandbox, protected by iOS Data Protection so they are readable only while the phone is unlocked (except the arrival file described under [Arrival codes](#arrival-codes)). Other apps and websites can't read them, Waypoint adds no encryption of its own, and the files can be part of your iCloud and computer backups. Opening saved trips needs no Face ID: the phone's lock is the gate. See [Offline](/Waypoint/start/offline/#in-the-iphone-app). The app deletes them when you sign out (**Use another Waypoint** and a 401 from the server included), when the server answers 401 or 403, when saving is turned off, when the server address changes and 3 days after each trip ends (the trip is dropped the next time the app reads the copy).

With no connection, the app shows the saved trips, read-only, instead of an error, from a copy of your server's public web app files that it keeps beside them (code only, no trip data and no token, deleted with the saved trips). Nothing is shown this way unless a trip is saved, and what appears is described under [With no connection, in the app](/Waypoint/start/offline/#with-no-connection-in-the-app). Starting the app with no connection works the same way when trips and the files are saved: the app waits about 5 seconds for the server to start its web session, then opens the saved page without a cookie or token, and goes back to the server (with a fresh web session) when it answers again. With nothing saved, or an error that isn't a lost connection, it shows the error as before; a 401 or 403 from the server signs you out and deletes the saved trips. Unit tests cover this; it has not yet been confirmed on a phone in airplane mode.

## Finding the places of your bookings

For the arrival codes planned in [#819](https://github.com/AnthonyPluth/Waypoint/issues/819), the app finds a street-level point for each parking lot, rental pickup and hotel on your saved trips, because the points your server keeps are only a postcode or city centre. This is the first part of [Arrival codes](#arrival-codes).

- **What is sent to Apple:** the text of the booking’s address, to Apple’s geocoder (the same service behind Apple Maps), from the phone, once for each distinct address that was found, and again for an address Apple could not find (or whose copy was removed) each time the app saves your trips, becomes active or location permission changes. This is the owner’s decision of 2026-11-18. Nothing else goes with it, except that, as with any request, Apple sees the phone’s IP address.
- **What is never sent:** the phone’s location. It is not sent to Apple, to your server or to anyone, and nothing is logged. Your server is not involved, and no other request is made.
- **When:** only while Waypoint has location permission (While Using or Always; there is no switch of Waypoint’s own), after each successful save of the trips, when the app becomes active and when location permission changes. Without permission nothing is looked up and any earlier result is deleted. The app asks for permission as [Arrival codes](#arrival-codes) describes.
- **Which bookings:** parking, rental pickups and hotels that aren’t cancelled and whose window hasn’t ended. A rental pickup with no address that can be found uses its airport’s coordinate when the saved trip has it (the saved copy carries the coordinates of the airports your car rentals name, see [Offline](/Waypoint/start/offline/)). A booking with neither is left out.
- **Where it is kept:** one file beside the saved trips, under the same file protection. It holds each place’s coordinates, circle and window, and the lookups cached by a hash of the address text, never the address itself. It is replaced with each save and deleted whenever the saved trips are (sign-out, a 401 or 403, saving switched off, a changed server address, 3 days after the trip ends).

## Arrival codes

When you get near a parking lot, rental pickup or hotel on your saved trips, the app tells you with one quiet notification, and tapping it opens the booking's code; opening Waypoint near the place puts a card at the top of Upcoming with one tap to the same code, so you don't have to dig for it.

- **What it does:** on an iPhone with location set to Always and Precise Location on, iOS tells the app when you enter a circle around a booking's address (parking 250 m, rental pickup 300 m, or 2 km around the airport when only its code is known, hotel 200 m), and the app posts one notification, with no sound and no badge, that names only the kind: “Your parking code is ready”, “Your rental pickup is near” or “You’re near your hotel”. It never shows the place, a name or a code. It is posted only inside the booking's window: parking from 2 hours before entry until exit, at most once every 4 hours; a rental pickup from 2 hours before to 4 hours after, once; a hotel on the check-in day from 3 hours before check-in, once. It is removed when the window ends, and only the 15 bookings with the soonest windows are watched (a rental pickup or hotel stops holding one of the 15 once its alert has fired, and its alert stays until the window ends). It works with no connection, from the saved trips.
- **What is asked, and when:** there is no prompt of Waypoint's own. The first time a save of your trips leaves a parking, rental pickup or hotel booking whose window hasn't ended, while the app is open (otherwise the next time you open it), iOS asks for your location (While Using), then straight away whether to also allow Always, then, once Always is allowed, whether Waypoint may send notifications (alerts only). Each is asked once per phone; nothing is asked while saving is off or nothing qualifies. If you keep While Using only, nothing is watched and no notification is posted.
- **Where your location goes:** nowhere. It never leaves the phone, is not sent to your Waypoint server or to Apple, and is not logged, and no track of where you were is kept: the app learns only that you entered a circle and, for the card below, asks iOS where the phone is once each time you open or return to the app while a booking's window is open, compares that with the circles in memory and drops it (it is not saved or sent, and nothing is asked while no window is open). The one thing it keeps is when each alert last fired (a time and the booking, in the arrival file below, so no record of an arrival beyond that alert time; the owner's decision, issue #849 comment, 2026-11-18), so a parking alert is not repeated within 4 hours and a rental pickup or hotel alert comes once; the entry goes when the booking's window ends, and every purge deletes the file. The one thing that goes to Apple is the booking's address text, to find its place on the map, as described in [Finding the places of your bookings](#finding-the-places-of-your-bookings). No server change was needed.
- **Tapping the notification:** the app comes forward and opens that booking's trip page with its code open. For parking it is the **Show QR code** dialog, with the picture saved on the phone when there is no connection (when none was saved for that booking yet, the dialog says so and shows the confirmation number); for a rental pickup or a hotel it is a dialog with the confirmation number large, a **Copy** button and the booking's details (“Show this at the counter.” or “Show this at the front desk.”). Waypoint holds no pickup code, locker code, room key or check-in QR, so the confirmation number is what it shows. It works the same on your server's page and on the saved page with no connection. Only the booking's number and its trip's number pass from the notification to the page, never a place, a name, a code or a coordinate. A parking booking whose code is not chosen yet, or a pickup or hotel with no confirmation number, opens only its trip page.
- **The card on Upcoming:** with While Using or Always and Precise Location on, opening or returning to the app while a booking's window is open and you are inside its circle puts one card at the top of Upcoming (on the saved trips' Upcoming too, with no connection): “You’re at” the place's name, “Your code is one tap away.” and a button (**Show QR code**, **Show pickup** or **Show check-in**) that opens the same dialog. It never opens the code by itself. One card at a time, for the booking whose window started last. **Dismiss** hides it until the app next finds you somewhere else and then back at a booking. The app answers the page with the booking's number and its trip's number only, and does the check at most once each time the app comes to the front.
- **No switch in Waypoint:** granting iOS's permissions is the opt-in, and iOS Settings is how to stop it.

| In iOS Settings → Waypoint, or in the app | What stops | What is deleted |
| --- | --- | --- |
| Location → Never (or Ask Next Time) | Everything: the watched places are dropped and every arrival notification is removed | The arrival file and the looked-up coordinates. Never a saved trip or the QR picture |
| Location → While Using (from Always) | The watching and the notification | Nothing |
| Precise Location off | The watching and the notification | Nothing; turning it on again resumes |
| Notifications off | The notification only | Nothing |
| Sign out, a 401 or 403, a changed server address, no server | Everything | The arrival file and the coordinates, with the saved trips |
| **Save my upcoming trips** off | Everything | The saved copy, and with it the arrival file and the coordinates |

Turning location back on in iOS Settings resumes watching the next time the app is opened or saves your trips, with no new ask. The app keeps an arrival file beside the saved trips so iOS can wake it for a place while the phone is locked: for each watched booking only its ids, kind, window, circle and when its alert last fired, never a name, address or code, readable after the first unlock since the phone started, and, like the saved trips, can be part of your iCloud and computer backups. The permission texts iOS shows are the two in the app's `Info.plist`. Region monitoring's wake-up while the phone is locked, its behaviour with Precise Location off and how late it fires have not been confirmed on a phone.

## Siri and Shortcuts

You can ask Siri about your next flight and your hotel, by voice or from the Shortcuts app. Every phrase includes the app's name, which Apple requires:

- **Next flight:** "When is my next flight in Waypoint", "Waypoint next flight" or "When do I fly in Waypoint". Siri says where it leaves from and goes to, the day and the time, as the departure airport's local time ("Your next flight leaves Denver for Grand Junction on Friday at 7:40 am, local time."). It is the next flight on any trip saved on the phone, whoever is on it. A phone that saved its trips before the app kept airport cities says the flight number instead of the cities.
- **Tonight's stay:** "Where am I staying tonight in Waypoint" or "Waypoint hotel". Siri says the hotel, its city and when you check out. With no stay tonight it says your next one.
- **Check-out:** "When do I check out in Waypoint". Siri says when you check out of the stay you are in, up to its check-out time in the hotel's own time zone; after that it names your next stay.
- **Open my trip:** "Open my trip to Grand Junction in Waypoint" or "Waypoint open Grand Junction". The place is the destination or name of a trip saved on the phone. Siri opens that trip in the app, and with two saved trips to the same place it asks which, naming their dates. The phone gives Siri only those destinations and names, replaced each time trips are saved and cleared when they are removed (sign-out, saving switched off, a changed server).
- **Parking code:** "Show my parking code in Waypoint" or "Waypoint parking". Siri says "Opening your parking at" and the lot's name, and opens Waypoint at the trip of the parking booking you are in (its entry passed, its exit not yet), else the next one, where **Show QR code** is. It never says or shows the code or the confirmation. The picture is saved on the phone with your trips, so **Show QR code** shows it with no connection too, on the saved trip's page as on your server's; when none was saved for that booking yet, the dialog says so and shows the booking's confirmation number. With no parking in the saved trips Siri says so and Waypoint still opens.

Siri answers only from the trips saved on the phone (see [Saved trips](#saved-trips)), so it makes no request to your server and works with no connection. The answer is as old as the last time you opened Waypoint online: the card under Siri's answer says how old, and says to open Waypoint once the copy is a day old. It needs saving to be on, and a signed-in app.

The phone must be unlocked: Siri asks for the unlock first, and the saved trips can't be read while it is locked. A HomePod can't unlock your phone, so it gets no answer.

Siri never says a confirmation code, a gate, a loyalty or Known Traveler number, a seat, a room, a phone number, a street address or another traveller's name. The card shows the stay's street address, the flight number, the times and the trip's name, and tapping it opens the booking in the app. Waypoint gives no trip to Spotlight, Siri's suggestions or Apple Intelligence. What you say and what Siri answers pass through Apple's Siri, as Apple's Siri settings describe.

## Ending it

The app's access ends when you can no longer sign in to Waypoint (you are taken off `OIDC_ALLOWED_EMAILS`, or, with groups, your last sign-in is older than `WAYPOINT_SESSION_DAYS`), or when the app drops the connection: it does so by itself when the server says the sign-in is no longer valid or when Waypoint answers 401 while you are using the app, and **Use another Waypoint** on its error screen signs out too. Each of these shows a "You are signed out of Waypoint" screen, and **Sign in** on it asks for the address again. There is no sign-out button in Settings yet. Unlike an assistant, the app does not appear under **Settings → Assistants**.

## Distribution (TestFlight)

You can put the app on your own iPhone through TestFlight with the "iOS TestFlight" workflow. It starts when a change to the iPhone app (`ios/` or its icon; Markdown-only changes under `ios/` do not count, and neither does changing the icon's SVG source alone: regenerate the PNG) is pushed to `main`, or by hand (Actions, **iOS TestFlight**, **Run workflow**, on `main`); never for a pull request. Changes to the web app alone do not start it, because the app loads your server and bundles no web files. It runs in a protected `testflight` environment that holds the signing secrets, and every run, automatic or by hand, waits there until the required reviewer clicks **Approve**. Only one upload runs at a time: while a run waits for approval a newer one queues behind it, and shows Pending with no Approve button until the older one finishes. If a newer push has queued behind a waiting run, cancel the older waiting run on the Actions page (Cancel workflow; it shows grey, not as a rejected deployment), then approve the newest once it asks. The version TestFlight shows is the latest Waypoint release when the run starts building (for example 3.49.0; normally the release made by the change that started the run, but if you approve before that release is cut it is the previous release, one patch behind, and the build number still rises), and the number in brackets is the build number, the workflow's run number, so TestFlight lists a build as 3.49.0 (87). If the latest release can't be read, the run stops with an error instead of uploading a made-up version. The build number rises with each new run; re-running a run keeps its number, and App Store Connect refuses a number it already has. It builds on GitHub's hosted Xcode 27 runner with Xcode 27.2 (App Store Connect requires the iOS 27 SDK for uploads from April 2027), archives a signed release, exports an `.ipa` and uploads it with an App Store Connect API key.

Setup happens once:

1. Join the Apple Developer Program and note your Team ID.
2. Register the bundle identifier and create the app in App Store Connect.
3. Create an Apple Distribution certificate and an App Store provisioning profile for that bundle identifier.
4. Create an App Store Connect API key with the App Manager role.
5. Create the `testflight` environment, restricted to `main` with required reviewers.
6. Add these secrets to it: `IOS_DIST_CERT_P12_BASE64`, `IOS_DIST_CERT_PASSWORD`, `IOS_PROVISIONING_PROFILE_BASE64`, `APP_STORE_CONNECT_KEY_ID`, `APP_STORE_CONNECT_ISSUER_ID` and `APP_STORE_CONNECT_KEY_P8_BASE64`. Add these variables: `DEVELOPMENT_TEAM` and `WAYPOINT_BUNDLE_ID`.

Until they exist, the workflow stops at its first step and names what is missing. The first run, started by hand on 2026-11-16, succeeded. The full checklist, with what each secret holds, is in the [iPhone app README](https://github.com/AnthonyPluth/Waypoint/blob/main/ios/README.md).

## Export compliance (encryption)

The app declares `ITSAppUsesNonExemptEncryption` as `false` in its `Info.plist`. This is the answer to Apple's export-compliance question, given once so App Store Connect does not ask on every build. It says the app uses only the encryption built into the phone: HTTPS, the Keychain and the system sign-in sheet.

The Waypoint web app has an offline vault that encrypts saved trips in a browser with Web Crypto (AES-256-GCM, ECDH, HKDF and a key derived from a passkey). The iPhone app does not use it: it sets up no passkey and its saved trips are plain files that only the phone's own protection (iOS Data Protection) guards, so the app adds no encryption of its own. The SHA-256 it computes only names folders and tags a saved build. The owner judged the declaration appropriate on that basis. This is not legal advice.

The declaration needs no change while the app adds no encryption of its own. Revisit it if the app ever encrypts the saved trips itself or runs the browser vault: the export-compliance questions would then be answered again for that build, and the annual self-classification report is worth considering.
