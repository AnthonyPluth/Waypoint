# Agent guide

Instructions for AI coding agents working in Waypoint, a self-hosted travel app for a household (Python backend in `waypoint/`, Svelte web app in `frontend/`). It shows the trips you're on (flights, hotels, rental cars, confirmation numbers), keeps the household's loyalty and Known Traveler numbers, and reads booking emails privately. Human contributors can use it too; [Development](docs/src/content/docs/contributing/development.md) has the long version, and the published docs are at https://anthonypluth.github.io/Waypoint/.

## Layout

- `waypoint/`: the backend, in packages whose imports `make lint` checks (import-linter's contracts in `pyproject.toml`):
  - `server/`: the HTTP handlers (`api/`), the route table and the background jobs. Nothing else in `waypoint/` imports it.
  - `domain/`: what Waypoint works out from your data (people and visibility, trips, the mail parsers in `mail/`, `demo.py`).
  - `providers/`: the outside services (`webpush.py`; Gmail and others as they come). A provider doesn't import another; what they share has a module of its own.
  - `storage/`: the database (`db.py`, `schema.py`, `models.py`, `settings_keys.py`, `secretbox.py`, `backup.py`) and `migrations/` (Alembic). It imports nothing above it, and only it imports the database drivers and Alembic.
  - At the top, what everything shares: `tls.py` (the only module that opens outbound connections), `validate.py`, `dates.py`, `monitoring.py`, `oidc.py`.
  - `static/`: the served assets.

  A broken boundary fails `make lint`: move the code to where its import is allowed rather than adding an exception. A new provider module gets a contract of its own naming the others.
- `frontend/`: the web app (Svelte, Vite, Tailwind, Vitest, ESLint). Its look is its own: tokens in `frontend/src/app.css`; the app is dark only (lint rejects a light palette and `dark:` variants).
- `tests/`: backend tests, run with `unittest`.
- `tools/`: scripts for the repo itself; `feature_map.py` generates the feature map, `api_contract.py` the API contract, `fleet_checks.py` the checks that replaced instructions.
- `docs/`: the documentation site (Starlight), published to GitHub Pages. Pages are Markdown in `docs/src/content/docs/`.

## Commands

Python goes through Poetry (Python 3.14).

- `make check`: each tool once: ruff, mypy, import-linter, Waypoint's own Semgrep rules, the fleet checks, the feature map's and API contract's checks, the Python tests (SQLite), the web app's type-check, ESLint, Vitest and build, and the docs site's build. Run it before pushing. The security scans (Semgrep's registry packs, Trivy, zizmor, pip-audit, npm audit, CodeQL) run only in CI.
- `make lint`: ruff, mypy, import-linter (the backend's import boundaries), ESLint and Waypoint's own Semgrep rules (`.semgrep/waypoint.yml`, run through `pipx`).
- `make test`: `poetry run python -m unittest discover tests`.
- `make test-parallel`: the same tests across 4 processes, as CI runs them (`make check` uses it), with coverage and its floor (`tools/coverage_floor.py`: 85% overall, 90% for each module in `waypoint/domain/`, `waypoint/providers/` and `waypoint/server/api/`); `make test-pg` runs them against `$DATABASE_URL` (Postgres).
- `make frontend-check`: type-check, lint, Vitest (with the coverage floor in `frontend/vite.config.ts`) and build for `frontend/`.
- `make fix`: apply ruff's safe fixes; review the diff afterward.
- `make verify`: runs the real app on demo data in a browser at phone and desktop widths, under `libfaketime` with the clock frozen on a fixed date (`waypoint/verify.py`; Linux only: `sudo apt-get install libfaketime`), so an image changes only when the UI or its data does. It writes, for each page at phone and desktop, a full-page image (`<page>-<width>.png`) and a first-screen image (`<page>-<width>-hero.png`, the one the README and the docs embed) to `docs/src/assets/screenshots/`, which is committed, and the report to `artifacts/verify/` (ignored). Before each page it sets up offline access in the browser with a virtual passkey, so the images show the app with offline access working. `PAGES="upcoming settings"` limits the pages, a run of every page first empties the images folder, and it runs on `VERIFY_JOBS` servers at once (default the CPU count, at most 4; `1` is serial; flows must not depend on each other's data). UI PRs commit the images it changed: see "Git and PRs" (demo data only).
- `tools/control`: drive the real app on demo data one command at a time (start a session, open a route, click, type, snapshot, screenshot, run a flow), to see your change working or reproduce a UI bug without writing a Playwright script. The [verify-waypoint skill](.claude/skills/verify-waypoint/SKILL.md) says when and how; `tools/control --help` lists the commands. It doesn't replace `make verify` (no accessibility audit, and the only source of the committed images). After changing its help, run `make verify-skill` (`make fleet-checks` fails on a stale `references/cli.md`); `make control-smoke` runs it end to end.
- `make fleet-checks`: the checks that replaced instructions (`tools/fleet_checks.py`, part of `make check`): one Alembic head, a test in `tests/test_migrations.py` for each migration, the workflows' conventions, the skills under `.claude/skills/` (well formed, and `verify-waypoint`'s `references/cli.md` equal to what `tools/control`'s help generates), the `Co-Authored-By` trailer on your commits since `origin/main`, no test removed or skipped on your branch without a `Removes-Test:` or `Skips-Test:` trailer saying why, and no image added or changed outside the places images belong (below).
- `make feature-map`: regenerate the feature map; `make feature-map-check` checks it is current and every route has a test (part of `make check`).
- `make api-contract`: regenerate the API contract (`docs/openapi.json`, `frontend/src/lib/api-types.ts`); `make api-contract-check` checks it is current (part of `make check`).
- `make docs`: the documentation site with live reload; `make docs-build` builds it and checks the links between pages.

## Starting work

- **One issue, one session.** Work starts from an issue made with the "Agent task" template (`.github/ISSUE_TEMPLATE/agent-task.md`): its scope, acceptance criteria, dependencies and the model to use (see [CLAUDE.md](CLAUDE.md)). Start a fresh session for each one, on that model, rather than running many pieces of work through one long session.
- **Decisions belong in the issue.** If the issue doesn't settle something a user would notice, ask instead of choosing. Otherwise keep existing behaviour exactly; a change that isn't asked for is a regression.
- **Done means checked.** An issue says how its result is checked (`make check`, `make verify` for anything on screen, a test that fails before the change); the PR shows that output, not a description of it.
- **Verify in proportion.** Run the tests your change touches while working, and `make check` once before pushing. CI runs the Postgres suites on every pull request: run `make test-pg` yourself only for changes to the database, migrations or tests (see "Tests that share the database" below), on a database of your own that you drop afterwards.
- **A correction becomes a check.** When a mistake is pointed out, fix it and add what would have caught it (a lint rule in `.semgrep/` or `frontend/eslint.config.js`, a test, or a check in `tools/fleet_checks.py`). A sentence here is the last resort, for what can't be checked.
- **Parallel work stays apart.** Agents working at once take separate areas. Two pull requests that change the same files, or both add a migration, land one at a time: the second merges `main` in and re-runs its checks.

## Working in a container

- **Start the session in the repository.** The session-start hook (`.claude/hooks/session-start.sh`) installs Python 3.14, Poetry's environment and the web app's packages, but only for a session whose project directory is this repository. A session started one level up has none of it: the system `python3` has no SQLAlchemy and `unittest` fails on the import.
- **Run Python through `poetry run` or `make`** (`make test`, `make test-parallel`, or `poetry run python -m unittest tests.test_x`), never the bare `python3`. `make setup` installs the dependencies by hand.
- **Subagents make their own worktree** under `.claude/worktrees/` (ignored by `.gitignore`), from the session's checkout, and push from there. A session whose working directory isn't a git repository can't create one for them.
- **Some checks only run in CI.** Locally: ruff, mypy, import-linter, Waypoint's Semgrep rules, the Python tests on SQLite, the web app's checks, the docs build, and the fleet, feature-map and API-contract checks. Only in CI: the Postgres suites (`make test-pg` needs a database of your own), the Docker image build and run, the security scans, and Codex's review of the pull request (see "Git and PRs"). A push reaches them; a local run doesn't.

## Start from the feature map

[`docs/feature-map.json`](docs/feature-map.json) (readable as the [Feature map](docs/src/content/docs/contributing/feature-map.md) page) lists every API route with its handler, the web app files that call it, the tests that exercise it and the docs page that describes it. Start there to find where a feature lives. It is generated: after changing routes, `api(` calls, tests or docs, run `make feature-map` and commit the result (`make check` and CI fail when it is stale). Every route has a test: `tools/feature_map_allowlist.txt` started empty and stays that way.

## Conventions

- No comments or docstrings in code (Python, TypeScript, JavaScript, Svelte, CSS): name things so the code says what it does, and put the why in the commit message, the PR or the docs. `tools/no_comments.py` and ESLint's `waypoint/no-comments` fail on one; a tool's directive (`# noqa`, `# type:`, `// eslint-disable-next-line`, `// @ts-expect-error`, `// svelte-ignore`) is not a comment. No docstrings either: a string that is a statement by itself counts. Match the surrounding code's style and naming. Ruff and mypy config live in `pyproject.toml`; don't silence a rule to get green.
- One paved path; lint fails on the old way (`.semgrep/waypoint.yml`, `frontend/eslint.config.js`). Fix a finding with the helper, or justify it with an inline ignore and a reason; don't switch the rule off. Python: HTTP only through `tls.urlopen` (no `urllib.request.urlopen` or `build_opener` outside `waypoint/tls.py`); request bodies in `waypoint/server/api/` through `waypoint/validate.py` (no `bool(body…)`, `float(body…)`, `int(body[…])`); no SQL built from strings (`sa.text(f"…")`); background jobs and provider modules take the `today` they're given (no bare `date.today()`); no `datetime.utcnow()`; month arithmetic only in `waypoint/dates.py`. Web app: `errMsg(e)` from `lib/act.ts`, not `(e as Error).message`; `fetch(` only in `lib/api.ts`; no `.catch(() => {})`, pass `ignoreFailure` from `lib/act.ts`.
- Real typography (’ – −) in user-facing strings and comments is intentional; don't "fix" it to ASCII.
- Schema changes need an Alembic migration in `waypoint/storage/migrations/`, numbered after main's newest, with its own `test_<revision>_…` in `tests/test_migrations.py` (checked). The history before the baseline, revision `0034` (`down_revision = None`), was squashed into it: the older migrations and their tests are in the repository's history, and `backup.restore` refuses a backup made at an older revision with a message saying so.
- The API contract: a route has its reply and body types in `waypoint/server/contract.py`, on its handler's annotations, and the web app calls it with `apiCall<"METHOD /path">(…)` from `lib/contract.ts`. Change a reply or body there, run `make api-contract` and commit the generated files (see [Development](docs/src/content/docs/contributing/development.md), "The API contract").
- A change users or contributors would notice updates its page in `docs/src/content/docs/` in the same PR. Link between pages with absolute paths (`/Waypoint/start/docker/`); a broken one fails the build.
- Add or update tests with the change. Don't skip, disable or delete a test to get CI passing; when one really goes, a `Removes-Test:` or `Skips-Test:` trailer says why (checked). A new route is held by `tests/test_every_route.py` without a test of its own for sign-in, the CSRF checks, its contract type and its docs page; it still needs tests of what it does.
- Never commit secrets. `.env.example` lists configuration; real values stay in `.env`.
- Read `SECURITY.md` before touching auth, encryption, mailbox access or anything that stores loyalty or Known Traveler numbers.

## Waypoint's promises

These are what the app is for; a change that breaks one is a blocking bug, whatever else it does. Each is held by checks that are in place before the code they guard (`.semgrep/waypoint.yml`'s "Waypoint's promises" rules, `tests/test_every_route.py`, `tests/privacy.py`), so the first pull request that adds a trip query, a Gmail call or a loyalty number is held to them.

- **Email stays on the server.** A message is read in memory for its booking, and what is stored of it is the booking's fields (a total the message states becomes the booking's cost: an amount, a currency code and that it came from an email) and its Gmail id. What the scan reads is decided by what a message says, not only who sent it: it lists all mail (not spam or trash, Promotions included), asks Google for just the subject, sender and snippet of each message, and fetches and reads only the messages those say are worth reading, read-only and in memory; a scan runs under a time budget (`BUDGET` in `domain/mail/scan.py`) and, when it runs out, the next one follows straight away (`scan.run`) until every message is looked at, backing off when Google says to slow down; a skipped message is remembered by its Gmail id alone and nothing of it is kept (a message from an ignored sender also keeps its sender's domain, until the ignore is undone, which deletes it), a follow-up to a booking the mailbox's owner can see (a message with no booking of its own whose text carries the confirmation code of one visible reservation from the same sender: one booking, or the legs of one booking in one trip that share the code; never one that says it changes or cancels, never matched on dates or names, a code that fits only a booking they can't see counts as no match) is remembered by its Gmail id and that booking's id (the reservation's first leg) alone and not stored, except that a total it states is added to the booking as its cost when the booking has none and the reservation is a single booking, and, for a parking booking, the one picture in it that looks like the gate's QR code (a PNG or JPEG of 100 to 1,000 pixels a side, near square, not repeated in the message: `qualifying` in `storage/gate_codes.py`) is kept with the booking, sealed under `WAYPOINT_SECRET_KEY` in `segment_codes`, never decoded, deleted with the booking, its mailbox and a trip's cleared emails, served only by `GET /api/segments/{id}/code` to those who can see the booking (404 for anyone else, blocked for assistants, absent from the offline copy, the calendar feed, reminders and what `/mcp` returns, which also never says a booking has one), a waiting Review item keeps beside its message only a keyed hash of the one confirmation code its text names (`reference_key` in `storage/stored_mail.py`), never the code, so items about one reservation show as one row, and the scan's summary is counts only (found, read, bookings, couldn't read, follow-ups attached, emails attached to an existing booking, skipped, cut short, how many of the mailbox's messages are looked at so far), never logged or shown with a subject, sender or text (the number of messages the AI was asked about and the number it dismissed as not bookings are counts too; a web push after a scan says only how many new Review items that hold a booking (incomplete, a match to settle, or AI suggestions to check) a person can see, `reminders.review_due`, with no subject, sender or text, and `tests/test_review_push.py` holds it inside `no_leaks`). The household can also pick some of a mailbox's own Gmail labels (`mailboxes.scan_labels`, label ids only, none by default, system labels never offered) to scan in full, bypassing the triage; the label routes answer only the mailbox's owner and are blocked for assistants. A forward is read as its first-level original (`unwrap` in `domain/mail/extract.py`), and a stay with no markup and no vendor parser may be read by `domain/mail/lodging.py`, which files complete bookings automatically without sender trust; incomplete bookings and ambiguous matches wait in Review. The message itself is kept only while something needs it: a review item waiting on it, or a booking made from it or added to by it (an email for a booking the mailbox's owner can already see is kept with that booking). What is kept is its subject, its sender's domain and day, its text (up to a hard cap per message, `KEPT_LIMIT` in `domain/mail/extract.py`, past which it is marked cut short) and, for an HTML message, markup rebuilt from an allowlist (`domain/mail/safe_html.py`: a safe subset of inline presentation (colours, fonts, sizes, spacing, alignment, tables and their widths) and nothing that runs or loads: no scripts, event handlers, `<style>` blocks, forms, `javascript:` or `data:` links or remote `src`) with the images it shows, as one value encrypted with `WAYPOINT_SECRET_KEY` (`storage/stored_mail.py`), in backups too. The images are the message's attached ones and the ones its markup names, which the server downloads once, when the message is kept, through the one module `providers/mailimages.py` (https only, public addresses only, size and time limits, PNG, JPEG, GIF and WebP only, no cookies or identifying headers); the browser never contacts the sender, so opening an email fires no tracking pixel, and what the sender can learn is only that the server fetched its image addresses once, when the message was kept. The app shows the message inline in the page, not in a frame: in an isolated shadow root that the web app fills by rebuilding the cleaner's output a second time from its own allowlist (`frontend/src/lib/email-render.ts`: the same tags and presentation, `https` and `mailto` links only, opened in a new tab with `rel="noopener noreferrer"`, and pictures only as `data:` images the app fetched from the authenticated routes), under the app's own Content-Security-Policy (no inline script, no remote images or fonts), so the cleaner, that second pass and the policy are what stand between a message and the app, with the images served by authenticated routes. A message kept before this shows its stored text and simple formatting without a missing-original notice. It is deleted, images with it, when its item is dismissed (unless a booking was made from it, which keeps it), when the last booking made from it is removed and when its mailbox is disconnected. It is never logged and never in the database in the clear. It is reachable from an AI assistant over `/mcp` only as the message (the subject, text and kept markup, never images) of a message kept for an item or booking that the connection's member can see, and only on a connection the household granted the `mail` scope: off by default, granted per connection in Settings with a plain warning that the email's text goes to the assistant that was connected, separate from `read` and `write`, and logged only as a count and the tool's name, never as content. Without `mail`, an assistant reaches a review item only as the fields Waypoint parsed from it (kind, provider, confirmation code, places, address, dates and zones, travellers, the sender's domain, why it needs review and the bookings it could match), never its subject, text, snippet or images. Whoever can see the review item or the booking can read the message, and no one else (404). The one other place it can be is a signed-in person's own device: the stored messages of the bookings on the trips saved there (every trip under way or starting within 7 days, and the next upcoming trip however far out, at most 10 trips; without their images) are part of the copy the app saves there (`GET /api/offline`, saved by `frontend/src/lib/offline.ts` through the encrypted store `frontend/src/lib/offline-vault.ts`), shown only to that person, never sent anywhere else, always encrypted on the device, and cleared on sign-out, when any request answers 401 or 403, when saving is turned off, and, for each trip, 3 days after that trip ends. Nothing sends email content to an AI except the optional AI fallback the household turned on (only its text, through the one module that does it, never images or markup; hosted, it goes through OpenRouter with the provider's training and retention off and is redacted first, but when the household sets the AI to Local (Ollama) the text goes unredacted and untrimmed to their own Ollama server), which sends a message only when a person presses Ask AI on its Review item, unless the household also turned on a second, separate switch, "Read unreadable mail with AI automatically" (off by default, offered only while the fallback is on, with a plain warning): then a scan also sends the text of a message that passed triage with a strong travel signal, that no reader produced a booking for and that is not a follow-up of a booking the mailbox's owner can see, in the same way as Ask AI (through `ai.suggest`, so the same redaction or lack of it for the chosen mode applies), with a failed request retried at most twice more (`TRIES` in `domain/mail/autoask.py`); an answer with no bookings that also says the email is plainly a promotion, a loyalty or account statement or a newsletter (`not_a_booking` in `ai.parse`) dismisses that one Review item and no other (`review.dismiss` with `only_this`, which deletes the stored message as any dismissal does, the scan still remembering it by its Gmail id), whether a person pressed Ask AI or a scan asked, and no error, timeout or unreadable answer ever does (`tests/test_mail_ai_dismiss.py`); with either switch off a scan sends no email text anywhere. An assistant on a connection granted `mail` (above) is the other exception. The one other thing that setting enables sends no email content: the trip destination's sparkle button, pressed by a person, sends only the trip's name (without its dates) and the cities, states and countries of its live bookings with their kinds, through the same module and with the same provider settings, never a confirmation code, a person's name, an email address, a street address or a loyalty number (`tests/test_trip_destination.py`). Checked: a corpus of hostile markup (`tests/hostile_markup.py`) that must come out of the cleaner and out of the inline renderer inert, with canary values that must never run or load (`tests/test_hostile_markup.py`, `frontend/src/lib/email-render.test.ts`), Google's hosts only in `providers/gmail.py`, AI hosts only in `domain/mail/ai.py`, image downloads (the public-only fetch) only in `providers/mailimages.py` (Semgrep's `waypoint-mail-image-fetch`), a message's body (`payload`, `raw`, decoded parts) only in `domain/mail/extract.py` and decrypting only in the storage layer (Semgrep), the message and image routes and `GET /api/offline` answer only those who can see the item or booking and are blocked for assistants, and the two routes that return a message's text to an assistant (`/api/assistant/review/{id}/email`, `/api/assistant/segments/{id}/email`) need the `mail` scope (`tests/test_mcp_routes.py`, `tests/test_mcp_review.py`, `tests/test_offline.py`), the gate code's picture is held by `tests/test_gate_codes.py` (rule, follow-up, sealing, backup, deletion, visibility, `/mcp`, canaries; no Semgrep rule of its own, decryption stays in the storage layer under the existing one), and a scan reaches the AI only with both switches on, in the request Ask AI makes (`tests/test_mail_ai_auto.py`), and a test of anything that reads mail runs it inside `tests/privacy.py`'s `no_leaks` with canary values in the body, the image bytes and the image addresses (the database counts only what is in the clear).
- **You see the trips you're on.** A trip is visible to the people on it (its people list, which always includes everyone named on any of its bookings), to whoever booked it or any of its bookings, and to whoever got the confirmation for one of its bookings in their own mailbox; nobody else, by any route. A solo work trip stays its traveller's. A trip's bookings are visible to everyone who can see the trip, and so is each booking's cost, and a member can move a booking into any trip they can see, or merge another trip into one, after confirming who will newly see what, which makes the booking's travellers people on that trip and lets the trip's people see the booking. The map's places, highways and state lines are bundled data read from disk (`waypoint/storage/places.tsv.gz`, `waypoint/storage/roads.tsv.gz`, `waypoint/storage/states.tsv.gz`); a trip's coordinates, road legs and the state lines near them reach the browser only in the visibility-checked `GET /api/trips/{id}/places` reply, and never go to an outside service. Checked: no trip or segment query in `waypoint/server/` outside the visibility helper (Semgrep); every route needs sign-in (`tests/test_every_route.py`); a trip's people include everyone on its bookings (`tests/test_trip_people.py`); the map's data is read from disk and nothing is sent out, and a stranger gets a 404 (`tests/test_geocode.py`, `tests/test_roads.py`, `tests/test_trip_roads.py`, `tests/test_states.py`, `tests/test_trip_states.py`).
- **IDs are for the household.** Loyalty and Known Traveler numbers are visible to every signed-in member (so anyone can book), encrypted at rest, masked until asked for, and never in logs, reports, notifications or hosted AI prompts (the one exception: when the household sets the AI to Local (Ollama), the email text goes to their own Ollama server unredacted, so a number written in it, and the saved numbers wherever the email writes them, reach that server and nowhere else; hosted OpenRouter mode still redacts them). Checked: decrypting only in the storage layer, `oidc.py`, `domain/loyalty.py` and `providers/gmail.py` (Semgrep); nothing kept in the browser's storage (ESLint); the one exception is the signed-in person's own copy of their upcoming trips, saved by the app through `frontend/src/lib/offline.ts` and encrypted by `frontend/src/lib/offline-vault.ts`, the only module allowed to use the Cache API, which never holds a loyalty or Known Traveler number (`tests/test_offline.py` checks `GET /api/offline` with canary values); `no_leaks` in the tests.
- **Times are where they happen.** A flight's times are wall-clock times at its airports, stored with the airport's IANA zone; nothing converts them to the server's zone or UTC on the way. Checked: no naive `datetime.now()` in domain or provider code (Semgrep), and those packages are fully typed (mypy).

## Mistakes that keep coming back

Review findings on agents' pull requests fall into the same few kinds. Check your change for each before you push. When one can be checked, it moves out of this list into a check (lint in `.semgrep/waypoint.yml` or `frontend/eslint.config.js`, or `tools/fleet_checks.py`); each item says which it is. The ones marked *human-judged* have no check: the independent review (`.github/workflows/agent-review.yml`) reads every agent's pull request for them, and a blocking finding fails the merge gate. The one push it doesn't read is one that only merges `main` in and leaves the pull request's own change byte for byte as last reviewed: that review's passing verdict carries over.

- **Failure paths** (human-judged). For every new error, rejection or early return, know what the user sees, and test it. Don't leave stale state that says things are fine: a scan that half-fails must not clear the last warning, a failed reload must not leave old trips on screen looking current, and a job that couldn't start isn't a failed run.
- **Tests that share the database** (human-judged). On Postgres every test module shares one database, and CI runs modules in parallel. A test that writes settings, or runs a mail scan or a request through the server, takes its own database with `tests/shared.py`'s `own_database(self)`: on Postgres that is a schema borrowed from the test process's pool (built once, emptied when the test ends, never shared by two tests that hold one at once), on SQLite a file of its own; a new database is made by `db.create_fresh`, not by replaying migrations. Run the Postgres tests before pushing a change to tests (docs/src/content/docs/contributing/development.md, which also shows the throwaway Postgres flags: for tests only, never for the image, the Compose files or a real database). In Vitest, use fake timers for anything debounced, so a save doesn't leak into the next test.
- **Private data in logs** (partly checked: lint sends every log line through `monitoring.log`, keeps `console.log` out of the web app, and keeps error-reporting and analytics SDKs out of the code and its dependencies, `waypoint-no-telemetry`; the rest is human-judged). Waypoint sends nothing about itself to any outside service. Logs and error pages never carry email content, traveller names, confirmation codes, loyalty or Known Traveler numbers, itineraries, query strings or credentials; that includes exception text (a database error names the row it was writing). Go through `monitoring.scrub` and `monitoring.report(values=False)`, and test what's logged or sent with `tests/privacy.py`'s `no_leaks`.
- **Personal data in the repo** (human-judged). The repository is public. Never put data read from anyone's instance or mailbox (names, emails, confirmation codes, record locators, flight numbers with dates, hotels and stays, loyalty or Known Traveler numbers, addresses) into PR titles or descriptions, review replies, issues, commit messages, code comments, tests, fixtures or docs, even to explain a bug. Fixtures are made-up emails with invented names, codes and numbers; real airport codes and airline names are fine. Describe a real case in general terms.
- **Visibility** (checked: Semgrep's `waypoint-trip-visibility`; a route's 404 for a trip you can't see is tested with the route). Every query for trips or segments goes through the one visibility helper; a route that takes a trip or segment id answers 404 for one you can't see, the same as one that doesn't exist.
- **Access that outlives the person** (human-judged). A new kind of session, grant, token, feed key or mailbox connection must end when its owner can no longer sign in (`oidc.access_lapsed`), like browser sessions do.
- **Time zones** (partly checked: lint rejects a bare `date.today()` in background jobs and provider modules and `datetime.utcnow()`; the rest is human-judged). "Today" and scheduled jobs' hours are the machine's local time (`TZ`); a booking's times are its airports' or hotel's. Anything that tells another system about a time (a calendar feed, a reminder) carries the right zone, not UTC by default.
- **Undo and restore** (human-judged). Putting something back restores exactly what was there, without normalizing it on the way; test the round trip with awkward values.
- **GitHub Actions** (checked: `tools/fleet_checks.py` checks bash by default, SHA pins with a version comment and paginated `gh api` lists; zizmor checks `persist-credentials`, template injection and pinning; concurrency groups and agents' allowed commands are human-judged). Workflows run bash with `-eo pipefail` (each file's `defaults`); keep it. On a pull request's `closed` event `github.ref` is main's, so build concurrency groups from `github.event.pull_request.number`. Check out with `persist-credentials: false`, pin actions by SHA with the version in a comment, pass event values to scripts as environment variables, paginate `gh api` lists, and allow an agent only the exact commands it needs. Run zizmor on a workflow you change.
- **Layout** (human-judged). A layout change is checked at phone and desktop widths, not only the one it was written at.

## Git and PRs

- Work on the branch you were given; don't push to `main`.
- Keep commits focused, with a clear message. An agent's commit ends with a `Co-Authored-By: Claude <Model> <version> <noreply@anthropic.com>` trailer naming the model that wrote it (checked on every pull request).
- Before pushing to a PR, run `make check`.
- A UI PR commits the images `make verify` changed in `docs/src/assets/screenshots/`, so a reviewer sees each page as before and after in the diff. The only images a change commits are the ones `make verify` writes there, which are the visual regression baselines: show a before and after through those images' diff, never a hand-made comparison file (`fleet-checks` fails a raster image that is not a `<page>-phone.png`, `<page>-desktop.png` or their `-hero` variant in `docs/src/assets/screenshots/`, or outside the logo catalogue, `waypoint/static/` and `docs/public/`). Only commit images of `make verify`'s made-up demo data: the repository is public, so nothing from a real instance. Skip it for a PR with no UI change.
- Open a PR for every change you're asked to make, once it's pushed, and summarize what changed and why. Keep the description short and professional: a few bullets on the change and how it was tested, not an essay. Don't say who asked for it or reported it.
- A PR's title decides the next version when it's merged: `feat: …` releases a minor version, `fix: …` or anything else a patch, and `feat!: …` (or a `BREAKING CHANGE:` line) a major one, for a change that breaks an existing setup.
- A PR is ready when its "Merge gate" check passes: every check green (`.github/scripts/merge-gate.sh`). Dependabot's updates merge themselves through it. The independent "Agent review" workflow is disabled (commented out in `.github/workflows/agent-review.yml`); Codex reviews pull requests instead (`chatgpt-codex-connector[bot]`, which comments on the PR, usually within a few minutes of opening it and again after each push). After opening a PR, watch it for Codex's comments: fix a P0 or P1 finding (or a P2 that is correct) and push, reply on its thread with what changed or why not, and leave nits alone unless the push already touches those files.
- Don't hard-wrap lines in PR descriptions, comments, issues or the body of a commit message: write each paragraph or list item as one line, and let GitHub wrap it to the screen. Only code and repo files keep their own wrapping. Keep the commit subject to one short line.
